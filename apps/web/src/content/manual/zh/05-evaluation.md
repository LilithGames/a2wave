# 评测

改了提示词、换了模型，Agent 到底变好了还是变差了？评测就是用来回答这个问题的：把一批「该问什么、该怎么答」的对话固定下来，每次改完配置跑一遍，横向对比结果。

评测入口在 Agent 详情页的 **评测** 标签页（位于「渠道」之后），内含两个子标签：**评测集** 和 **评测任务**。

## 两个概念

| 概念 | 是什么 |
|------|--------|
| **评测集** | 一批评测用例的集合，比如「客服场景」「代码审查场景」。 |
| **评测用例** | 一段对话。包含一到多轮「请求 + 期望应答」。 |
| **评测任务** | 用 Agent 当前配置把某个评测集跑一遍，记录每轮实际应答。 |

## 建评测集与用例

1. 打开 Agent 详情页 → **评测** → **评测集**。
2. 点 **新建评测集**，填名称（如「退款场景」）。
3. 点 **新建用例**，填用例名称，然后写第一轮的：
   - **请求**：用户会说什么。
   - **期望应答**：Agent 应该怎么回。期望应答可以留空，表示这一轮只是铺垫上下文。
4. 需要评测多轮对话时，点 **添加一轮** 继续往下写。轮次可以上移、下移、删除。

> [!TIP]
> 期望应答不必逐字精确，写清楚「关键点是什么」即可——评审时是你自己对照实际应答判断，不是做字符串比对。

### 多轮用例怎么写

多轮用例用来验证 Agent 是否记得上下文。例如：

| 轮次 | 请求 | 期望应答 |
|------|------|---------|
| 1 | 我要退款，订单 #123 | 先询问下单日期，不要直接答应 |
| 2 | 40 天前买的 | 说明超过 30 天退货期，改为提供补偿方案 |

执行时这几轮会在**同一个会话**里依次发出，所以第 2 轮能接上第 1 轮的上下文。

## 跑评测任务

1. 切到 **评测任务** 子标签，点 **发起评测**。
2. 选择评测集，可选填任务名称（如「基线」「换 Sonnet 试试」）。
3. 点 **开始运行**。任务在后台按用例逐条执行，页面会自动刷新进度。

执行期间任务详情页会显示 **进度条 + 已完成数量**，并标出当前正在跑的是哪条用例；用例列表里，正在执行的用例带转圈图标，还没轮到的显示「等待中」。

**排队**：同一个 Agent **同时只跑一条** 评测任务，这个数量不可配置。因为一条任务会独占自己的工作区直到全部用例重放完，并发跑会让两条任务互相干扰、结果不可比。其余任务状态是 **排队中**，前面的任务跑完后会自动开始，不需要你再点一次。不同 Agent 之间各排各的队，互不影响。

任务执行期间可以 **取消**：排队中的任务立即取消；正在执行的任务在当前用例跑完后生效，不会从中间打断一次对话。任务终止后（取消或失败），还没轮到的用例会标记为 **未执行**，不会一直停在「等待中」。

> [!NOTE]
> 如果服务在评测执行途中重启，正在跑的任务会被标记为 **失败**（原因写明「被服务重启中断」），不会一直卡在「运行中」。重新发起即可，已经跑完的任务和评审结论不受影响。

> [!NOTE]
> 任务创建时会冻结当时的 **Provider + 模型 + 提示词**，执行时按这份快照跑，因此排队期间修改 Agent 不会影响已提交的任务。但如果快照里的 Provider 在任务开始前被移出该 Agent，任务会 **失败** 并说明是哪个 Provider 不可用——而不是换一个 Provider 跑完、却把结果记在原来那个头上。

> [!NOTE]
> 评测使用的是 Agent **当前已保存**的配置，不需要先发布。如果你刚改完配置还没保存，请先保存再发起评测。评测执行不会出现在[运行记录](/wiki/runs)里，也不会计入统计和排行榜。

## 评审结果

任务跑完后，点进任务详情，每条用例可以展开，看到每一轮的 **请求 / 期望应答 / 实际应答** 并排对照。

确认无误就点 ✓ 标记 **通过**，不符合预期点 ✗ 标记 **不通过**。待评审的用例会排在最前面，方便你从上往下过一遍。

顶部会实时统计 **通过 / 不通过 / 待评审** 数量与通过率。通过率只按已评审的用例计算——刚跑完还没评审时显示「—」，而不是 0%。

## 对比不同配置

这是评测真正的价值所在。每个评测任务都会冻结一份 **配置快照**，记录当时的：

- **Provider**（执行引擎）
- **模型**
- **系统提示词**

在任务详情页展开「配置快照」即可查看。任务列表按时间倒序排列，直接对比不同任务的通过率，就能看出哪套配置表现更好。

当某个任务相对上一次任务的配置发生变化时，列表里会标出 **模型有变更** 或 **提示词有变更**：

| 任务 | 模型 | 通过率 | 标记 |
|------|------|--------|------|
| 回归验证 | Sonnet | 11/12 92% | |
| 提示词 v2 | Sonnet | 9/12 75% | ⚠ 提示词有变更 |
| 基线 | Opus | 11/12 92% | ⚠ 模型有变更 |

> [!IMPORTANT]
> 有这个标记才能正确解读分数波动。上表中「提示词 v2」通过率下降，原因是提示词改了，而不是模型退化——没有标记的话很容易归错因。

> [!NOTE]
> 配置快照只记录 Provider、模型和提示词，**不含任何密钥**（API Key、OAuth Token 等一律不落库）。挂载的 Skill、MCP、知识库不在快照范围内。

## 权限

评测遵循 Agent 本身的[成员权限](/wiki/members)：

| 角色 | 能做什么 |
|------|---------|
| 查看者（viewer） | 查看评测集、用例、任务与结果 |
| 编辑者（editor） | 以上全部，外加增删改评测集/用例、发起与取消任务、标记评审结论 |
| 所有者（owner） | 全部权限 |

## 排错

**跑出来的用例状态是「执行失败」**
展开该用例可看到错误信息。常见原因是 Provider 凭证失效或模型不可用——先到「配置」页确认 Provider 与模型能正常工作，可用[调试对话](/wiki/agents)验证。

**多轮用例只跑了前几轮**
某一轮失败后，该用例剩余轮次会停止执行。因为后续请求依赖前一轮建立的上下文，继续发下去只会得到无意义的应答。修复失败原因后重新发起任务即可。

**删了评测集，历史任务还在吗**
在。任务会保留当时的评测集名称与全部结果，方便回溯。
